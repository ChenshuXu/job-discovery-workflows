# Interview Research & Prep

让 用户 打开文档就知道：已约的每一轮怎么面、先准备哪些具体问题、近期实际考过什么、
哪些问题在可比面经样本中重复出现，以及每项判断的来源。详细证据账独立存为一个文件，
prep 从它归纳 Coding、System Design、BQ 三类题单，每类从最重要到最次要排列。
每题首行使用原生 Markdown 复选框记录进度，详情顶格写在任务项外，避免勾选后正文被划掉；
修订时保留已勾选状态、个人笔记和答案。
交付文档在 Obsidian 中阅读，按 contract 使用库内 Wikilink、标题链接及 Q-ID/S-ID 块链接。
写作或修订时复用已安装的 `obsidian-markdown` Skill（从当前宿主的 Skill 列表定位其 `SKILL.md`）的语法规范。
保证写入文件符合 Obsidian 格式即可，不执行该 Skill 的阅读视图验证，也不要求 CLI 或界面验收。

## 按请求选择范围与读取内容

Skill 的唯一源文件在 Job Discovery；交付物在 Career Docs 的 `context/Interview/<company>/`。

- **新调研 / 最新面经**：锁定身份与轮次，先读缓存，再按来源缺口读取
  [联网流程](references/research-workflow.md)并派发；三路都有工作才并行启动三名来源 worker。
  各 worker 自主完成本批查询、翻页、采集与覆盖自查后交付；本批来源均结束或真实受阻、
  材料固定后，主代理才统一做 LC 核对、跨帖归并、频次、排序与文档整合。具体缺项才定向补查。
- **单平台补查**：只派该来源负责人，保留其他来源成果和既有 ID。
- **按新 contract 对齐 / 修订已有 prep**：使用下节离线修订流程；Skill 更新不自动触发联网。

| 角色 / 模式 | 必读范围 |
|---|---|
| 主代理修订 | 本入口、当前 contract；先对照全部适用要求确定影响范围，再细读受影响规则 |
| 主代理新调研 | 本入口、联网流程、contract；归纳前完整读取第 2 节排序与频次口径 |
| 来源采集 worker | 派发中的身份/轮次、缓存与缺口；联网流程“派发与协作”、第 3–4 节的共同规则及所属平台细则；contract 第 4–5 节；capture-step 与 Ego Skill |
| 离线修订 worker | 派发中的变更范围、目标及原件定位、当前 contract 相关章节；不读联网/Ego 规则，不读取无关个人资料 |
| 原件反查 worker | 当前版本受审条目、关联原件、contract 第 4–5 节及本次变化的语义口径 |

主代理把必读路径与章节直接写进派发消息；worker 不必再全文读取本入口及无关输出规则。
来源字段只在 [document contract](references/document-contract.md) 维护，不再复制一份 worker schema。
小范围直接修订即可，不为并行而派代理；可独立完成的批量格式调整、证据补提取和逐源反查交给 Luna Max。

## 按当前 contract 离线修订

1. 确认用户指向的公司、职位、轮次及既有 prep/证据账；修订历史准备文档时沿用其身份，
   不替换成当前另一场活跃面试。读当前 contract 对照两份文档；有旧 contract 时用差异缩小
   范围，没有则逐项检查当前适用要求，不要求补造旧版本或重新调研。
2. 在本次修订说明中简记“规则变化 → 受影响文档/字段/S-ID/Q-ID → 所需操作”；不另建台账。
   - 格式、标题、链接、字段位置：直接调整或交给一名离线 worker；不因此重读全量原件、重判题意。
   - 新证据字段、遗漏追问：从现有证据索引定位原文/图片，只补提取受影响来源；未知仍标未知。
   - 轮次、LC 对应、去重、频次或排序口径：worker 整理带原件定位的候选变化，主代理核对并决定。
     影响范围包含相关来源组、计数、双向引用及排序邻项；全局规则变化就覆盖所有受影响题目，不能只抽几题。
3. 需要离线 worker 时复用可用且职责合适的原 worker；否则新派一名 `gpt-6-luna` / `max`，
   使用 `agent_type: "default"`、`fork_turns: "none"`，用户本轮指定优先。检查运行时支持并核对
   实际返回设置，无法确认则注明；不静默换模型。该角色不依赖三来源配置，不启动三路采集。
   明确它不是唯一工作者：只写指定临时草稿/差异文件，不改 canonical、原件、tracker、记忆或
   其他 worker 文件，不嵌套派生。传当前规则、影响范围、相关文件和定位，避免继承全段对话。
   返回改动条目、原件定位与缺口；主代理负责合入 canonical，语义决策不交给格式 worker。
4. 按稳定 Q-ID 保留勾选、个人笔记和答案。拆题/合题按 contract 迁移，不能把旧完成状态
   推断给新任务。原件冻结不改；prep、证据账及派生映射可更新。不全量重写无关部分。
5. 缺口先查其他已有归档及人工供稿；仍缺且影响本次修订时才按联网流程补该来源。
   用户明确只用缓存时列出待补项，不联网。只有要求最新面经或确有证据缺口才增量搜索，
   不把更新 Skill/contract 当作缓存失效。
6. 回查受影响原题与追问，检查计数、链接及进度保留；格式-only 变更只做内容保留和机械检查。
   修正后只重查新增影响范围。记录原采集日期、本次修订日期、当前 contract 路径、变更与
   未解决项，不把修订日改成采集日；最终分别说明离线对齐、语义复核和机械检查的实际范围。

### 归档作为缓存

- 缓存使用公司目录中现有的 `research-<日期>/` 和历史来源归档，不另建数据库或复制整个
  缓存。先按原帖 URL/平台帖子 ID 查来源账、worker ledger 和原始文件；S-ID 可能只在
  某次 run 内唯一，不能仅凭同号合并。传给 worker 的任务包括已有缓存位置和真正待查项。
- 原始页面文本/截图是重新归纳的依据，worker 摘要、题目映射与旧 prep 都是可修订的派生
  结果。按 contract 核对原件是否存在、可读、来源相符及可见范围。旧索引
  指向临时路径时，先定位并核对已归档副本，再修订新文档引用，不改冻结原件或直接重抓。
- 充分缓存的来源直接复用；部分缓存只补缺页、缺图、缺评论或缺少的题意。记录每项为
  缓存命中/部分命中/缺失/待更新，缺索引先补定位，不将已存原文重新采集一遍。
- 恢复失效链接时，以帖子 ID 搜索原始页面/卡片记录，核对实际 href 及签名是否已被
  `[REDACTED]` 替换；保留参数名不代表完整可用，脱敏 URL 不用于导航。已有完整签名链接
  仅在内存中用于该原帖，不回显或另存签名。签名缺失/失效且没有
  当前访问限制时，从正常搜索或已记录作者入口重新定位同帖；不猜 token、不拼替代地址。
  这些恢复入口确实无效后才请求用户供稿，不能只读旧 ledger 就认定原始链接不存在。
- Skill 版本变化不使原文缓存失效。请求最新面经时搜索上次采集后的新增来源，仍覆盖所需
  时间窗；旧帖只在有更新线索、待解冲突或明确刷新要求时重访。新版本另存并保留旧快照，
  同帖不新增频次；缓存读取日不改写原采集日，报告明确本次离线修订/增量采集及覆盖截止。
- 增量更新保持三个来源分工，分别读取各自上次覆盖截止，以本次采集开始时间为固定上界，
  按发帖时间收集新增帖子；边界日期精度不足时重叠该日期并按原帖 ID 去重。面试日期用于
  题目排序，不作为发现新帖的时间依据。上次受阻/未完成区间单列续查，不用任务结束时间
  冒充覆盖截止；首次或无可靠覆盖记录时按实际缺口与默认时间窗采集。各路记录查询范围、
  实际覆盖截止和遗留缺口；新增材料固定后沿用统一整合流程，只重核受影响的题目、计数和排序。
- 本流程不生成、校验或要求 SHA-256 等文件摘要；用原帖 URL/S-ID、文件路径、采集时间和
  修订记录追踪材料。历史摘要清单可保留，但不作为缓存复用、修订或验收的前置条件。

## 锁定公司和已约轮次

先定位 `job-discovery/` 仓库根目录；本节 `../career-docs/` 和 `.agents/` 相对于该根目录，
Career Docs 内部的 `context/` 相对于 Career Docs 根目录。非同级布局使用已解析的实际路径。

- 读 `../career-docs/AGENTS.md`，通过 `context/00 Knowledge Base Hub.md`
  定位资料，再只读 `context/Interview/active-interviews.md` 和该公司相关文档。
- 从用户本轮说明、邀请、recruiter 消息、附件和 JD 确认公司、职位/级别、team、requisition
  或准确 tracker identity、已约轮次、日期/时区、面试官、时长及平台。用户指定的范围优先；
  公司有多个职位且无法消歧时才问一个简短问题。未提供公司时先问公司，不自行选择活跃面试。
- 默认覆盖该身份下接下来已约的所有轮次，逐轮分配 R1、R2 等 ID。不要把历史面试或尚未约的
  后续轮次写成已约。邀请含多场 loop 时分别识别；OA/take-home 保留截止时间，不虚构开考时间。
- 旧 prep doc 是线索和可复用结构，不是新的证据；优先回查其原始归档，按缓存规则决定补查。
  复用同一身份/轮次的 canonical prep 与独立证据账，保留已存在的进度、个人笔记和答案；其他轮次另建文档，
  不批量重写整个 Interview 目录。
  本轮 research refresh 和各平台 inventory 增量分别合入这两份文档，不另建平行题库。
- 只读流程登记表。涉及登记变更，路由到
  `.agents/skills/gmail-job-reply-review/SKILL.md`。

## 按题意找 LeetCode，并保留待确认项

新调研逐题执行；修订仅处理受影响映射。纯格式更新不重新查题，需联网时先读取联网流程。

对每个 coding 题主动按描述、接口、约束、例子及原始题号/谐音查找对应题，不能等原帖明确
给了 LC 编号才查。先复用已存 LeetCode 原页证据；不足时用 Ego Lite 搜索、打开候选页。
核对任务、输入输出、关键约束
与变体，返回题号、标题、链接及匹配依据；查不到精确对应时标 custom / 尚未找到，保留原题。
每题在已有条目记录检索定位与状态：已核对精确/变体、仅 proxy、检索后未找到、题意不足，
或尚未检索/受阻。只有题名也尝试按原词检索；信息不足不能补造任务，尚未查过不能写成
已查无对应。按待查题逐项收尾，访问了若干 LC 页面不能替代全部适用题目的核验。
原词/题意定向检索及有依据的候选核对后，若没有新的匹配线索，标“未找到”或“题意不足”并结束
该映射；不为取得精确 LC 编号反复换词或展开无关题库。只有新增题意/候选证据才重开核对。

一亩三分地常用谐音、暗语或残缺题号：始终保留原词和上下文。不能确定时在原题同一条目
列“候选 LC + 链接 + 匹配点/疑点 + 待 用户 手动确认”；没有可靠候选就原样留着，
不强猜、不删掉、不因等待确认而停止其他题的采集。用户 确认后记录其确认及日期再合并。
可靠题意匹配或明确题号可标已核实；未经确认的候选不能贡献某个确切 LC 的频次。

标准题的题意、例子、约束标为“LeetCode 标准题补充”，面经原题与现场变体单独保留。
follow-up 按实际提问顺序随主问题保存，包括新约束、复杂度、测试、扩展接口及设计追问；
如追问对应另一道 LC，也主动查找并挂在该主问题下。区分面试官追问、评论补充/猜测和作者
事后建议；相似练习题标 proxy，不冒充原题。保存忠实转述，不补全不可见题意，不全文复制帖子。

## 判断形式，生成准备题单

按 document contract 将每轮形式标为“已确认 / 推断 / 未确认”，逐项引用直接证据。
邀请通常比泛化面经更适用于 用户；证据冲突时保留差异，检查时间、团队、级别和地区。
无明确说明时给出有依据的最可能形式和待确认点，不只写一句“technical interview”。

生成前，主代理给每个原始问题及追问明确对应的 S-ID/原条目标识、来源轮次、日期、归属与
Q-ID；不同轮次先分开，未知不继承同帖另一轮日期。自动匹配只能提出候选：任务、输入输出、
规则及现场语境支持后才能合并，不能仅凭 finance、transaction、API 等共同词归为一道题。
若使用生成脚本，只消费已核对的映射来排版和计数，不从散文重新猜轮次、题号或归属；例如
invoice 不证明 VO，300 秒不证明 LC300。LC 链接只来自明确的题号/URL字段。

归一化相同问题并保留变体。每个题单条目给出具体题目/问法、所需准备范围、明确出现过的
follow-up、近期日期、去重计数、匹配边界和 S-ID。按 Coding → System Design → BQ 分设题单，
每题保留适用 R-ID，不再按轮次切散三类题单。本轮具体明确要求优先；可比亲历原题先按近期性，
同时间档内按同级别Loop、相邻级别Loop、同级别Screen/OA、未确认排序，再看证据确定性、
独立重复及团队匹配。日期/级别/轮次必须绑定同一经历，不用旧同团队题跨档压过近期原题。
“优先准备 / 接着准备 / 有余力再看”从证据导出，不固定名额；每题说明可回查的排序理由。
完整顺序、日期替代与补充范围遵循 contract 第 2 节。覆盖所有已发现问题类型；未发现某类型
要写“未找到本轮报告”，不能写“不会考”。不要用未经校准的分数或押题概率。

频次完全按证据账计算，具体口径见 contract。近期考题、高频信息和准备顺序合在所属类别题单，
通过 source ID 跨文件链接详细证据，证据账反向链接 prep 的 Q-ID；完整来源库存和历史覆盖
记录不放进 prep。不另复制近期榜、高频榜或优先级榜，归纳不能删掉原始报告中的题目与限定条件。

默认产出研究、题单与准备目标，不自动写完整解法、BQ 答案、mock 或练习代码。
用户另要答案时遵循 Career Docs 的 `interview-prep-writer` 和适用 methodology，个人经历只能
来自 用户 或其已核实的个人证据，不能把别人的面经答案写成他的故事。

## 反向核对与交付

联网实跑时，主代理将已生成的 prep 与证据账路径、归档原件和 S-ID 对照发回本次实际参与的原 worker，做离线逐源审查。
涉及语义或证据变化的缓存修订，按离线流程由当前代理或指定 worker 从原件反查受影响项；不以原 worker
不可用为由重跑采集或阻止修订，也不声称没有发生的原 worker 审核。
worker 从自己实际读到的题目和每个 follow-up 出发，按 contract 的覆盖规则对应 Q-ID；
回报具体缺项、错误映射/日期/归属或未读范围。只核对题单自身、只返回“PASS”或已读文件数
不够；原帖有题而题单没有，就是漏题，即使证据账已收录。复核用工具消息交回，不改采集原件。
另查没有 Q-ID 的记录及“不计题”项：逐项注明无题、范围外，或拆分后对应的新 Q-ID。
仅披露 topic/营销题型仍按 contract 归纳，不能因没有完整题面而留空；原子条目存在、字符串
仍出现在证据账和映射总数一致都不能替代这项审查。
复核注明所读文档路径、修订时间和实际覆盖范围；后续修正只重查受影响条目及其计数、引用，
不能把旧版本 PASS 直接用作最终版本的全量结论。跨源同组的性质、日期和频次由主代理复核。

主代理修正后重查受影响项，再完成以下适用检查；纯格式修订不重新执行搜索覆盖及全量语义核验：

- **搜索覆盖**：本次采集 worker 的入口、已约题型查询、相关待查项和停止原因通过联网流程第 4 节检查。
  按联网流程的查询终点、重要待查项和全局收尾条件验收，不把仍有链接等同于必须继续；真实阻碍标部分完成。
- **语义与频次**：逐题核对 Q-ID 与原始问题对应关系，保留不确定题和营销题；按逐题来源/
  去重组及其各自日期重算次数、构成、最近日期与时间窗。追问/标准题/proxy不能互相替代。
  跨站去重由主代理统一判定，worker 不各算一份再相加；高频与关键映射抽查原页/图片证据。
- **文档**：按 document contract 检查题单分类与实际排序、准备进度保留、prep/证据账分工、
  引用、确认等级及覆盖缺口；完整字段与格式只在 contract 维护。
